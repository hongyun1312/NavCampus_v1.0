### 阶段 1：A* 算法工程化落地（第 2 周 · 约 20h）⭐ 最高优先级
**目标**：把简历上"写了但没实现"的 A* 算法真正做出来，形成"论文 -> 工程落地"闭环，拆掉这颗定时炸弹。

4. **封装为可复用 SDK（2h）**

### 阶段 2：中间件深度应用（第 3-4 周 · 约 40h）⭐ 主轴
**目标**：在智慧校园里落地"消息队列 + 分布式锁 + 限流 + 分布式事务"，把简历从"用了 Redis 缓存"升级到"中间件深度实践"，最对口"中间件"目标方向。

**任务清单**：

#### 2.1 RabbitMQ 消息队列削峰（12h）
**场景设计**：校园导航高峰期（如新生开学、课间）并发路径规划请求激增，同步处理会压垮后端。

**落地**：

+ 引入 RabbitMQ，把"路径规划请求"改为异步：前端提交规划任务 -> 落库 + 发 MQ 消息 -> 消费者异步计算路径 -> 结果写回 + WebSocket/轮询通知前端
+ 实现**死信队列**：规划失败/超时的任务进死信队列，便于排查
+ 实现**延迟队列**：用 rabbitmq_delayed_message_exchange 插件做"导航结果过期清理"

**面试话术**：

> "导航请求高峰期我用了 RabbitMQ 削峰，同步改异步，前端提交规划任务后落库发 MQ，消费者异步算路径，结果通过轮询返回。配了死信队列处理失败任务，延迟队列做过期清理。这样把瞬时高并发从同步阻塞变成平滑消费。"
>

**量化指标**：同步 vs 异步在 500 并发下的接口 RT 对比、后端 CPU/内存占用对比

#### 2.2 Redis 分布式锁进阶（Redisson）（8h）
**场景设计**：多个用户同时规划路径，可能命中同一份地图缓存，需要分布式锁防止缓存击穿时的并发重建。

**落地**：

+ 用 Redisson 实现分布式锁（替代手写 SETNX）
+ 实现**缓存重建加锁**：缓存失效时只允许一个线程重建，其他等待
+ 实现**看门狗机制**理解（Redisson 自动续期原理）
+ 对比手写 SETNX 的坑（原子性、超时、误释放）

**面试话术**：

> "缓存击穿防护我用 Redisson 分布式锁，热点 key 失效时只放一个线程去重建缓存，避免大量请求打到 DB。选 Redisson 而不是手写 SETNX，是因为它解决了锁超时、误释放、可重入这些问题，看门狗自动续期避免业务没执行完锁就过期。"
>

#### 2.3 接口限流（6h）
**场景设计**：防止恶意刷接口（如疯狂调用路径规划）。

**落地**：

+ 实现**令牌桶限流**（可用 Redis + Lua，或 Sentinel）
+ 对路径规划接口限流（如单用户 10 次/分钟）
+ 可选：接入 Sentinel 做熔断限流（顺带补"微服务"标签）

**面试话术**：

> "接口保护我做了令牌桶限流，用 Redis + Lua 保证原子性，单用户每分钟限 10 次规划请求。也了解了 Sentinel，它的滑动窗口统计和熔断降级更完整。"
>

#### 2.4 分布式事务场景（本地消息表）（10h）
**场景设计**：路径规划任务落库 + 发 MQ 消息，这两个操作需要保证最终一致性（不能落库了但消息没发出去）。

**落地**：

+ 实现**本地消息表**方案：业务表 + 消息表在同一个本地事务里写入，定时任务扫描消息表补偿发送
+ 或用**事务消息**（RabbitMQ 事务/confirm 机制）
+ 理解各种分布式事务方案对比：2PC / TCC / Saga / 本地消息表 / 事务消息

**面试话术**：

> "规划任务落库和发 MQ 之间我用本地消息表保证最终一致性，两者在同一个本地事务，定时任务扫描未发送的消息补偿。我对比过 2PC、TCC、Saga、本地消息表，选本地消息表是因为它简单可靠、不需要额外事务协调器，适合这种最终一致场景。"
>

**量化指标**：异步削峰 RT 对比、限流效果、消息可靠性（无丢失）

**工时**：约 40h（2 周）

**简历 bullet（新增）**：
